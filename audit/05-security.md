# 05 — Security Audit

## Overview

Security is the weakest aspect of this application. The entire app has **zero authentication**, **zero authorization**, **zero input sanitization on the server**, and **zero CSRF protection applied to any form**. Given that this is a **health application dealing with children's medical data**, the security posture is critically inadequate.

---

## Findings

| Finding | Severity | File/Line | Impact | Recommendation |
|---------|----------|-----------|--------|----------------|
| **OWASP A01: Broken Access Control — ALL routes are public** — There is no `auth` middleware applied to any route. `/admin`, `/screening-anak`, `/monitoring`, `/laporan-evaluasi` — all accessible without login. | Critical | [web.php](file:///Users/aldriknoel/EmoGrow/EmoGrow/routes/web.php) L1–68 | Complete unauthorized access to all functionality. Any internet user can access any page. | Apply `auth` middleware to all routes except login/register. Add role-based middleware for admin routes. |
| **OWASP A01: Client-side role check** — Admin access is gated by `localStorage.getItem('userRole') !== 'admin'` in the Sidebar and by `email === 'admin@emogrow.com'` in AuthPage. Both are trivially bypassable. | Critical | [Sidebar.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Components/Layout/Sidebar.tsx) L109, [AuthPage.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Auth/AuthPage.tsx) L96 | Any user can grant themselves admin access via browser DevTools. | Implement server-side RBAC with Laravel policies, gates, and middleware. Never rely on client-side role checks. |
| **OWASP A02: Cryptographic Failures — APP_KEY committed to `.env`** — The `.env` file contains an `APP_KEY`. Although `.env` is in `.gitignore`, the file itself exists in the workspace. If this repo is ever shared or pushed, the key is exposed. | High | [.env](file:///Users/aldriknoel/EmoGrow/EmoGrow/.env) L3 | APP_KEY is used to encrypt cookies, sessions, and other data. If compromised, attackers can forge sessions and impersonate any user. | Rotate the APP_KEY. Ensure `.env` is never committed. Use environment variables in production. |
| **OWASP A02: SESSION_ENCRYPT=false** — Session data is stored unencrypted in the database. | Medium | [.env](file:///Users/aldriknoel/EmoGrow/EmoGrow/.env) L32 | Session data (including user ID, auth state) can be read by anyone with database access. | Set `SESSION_ENCRYPT=true` in production. |
| **OWASP A02: Empty DB_PASSWORD** — MySQL root user has no password configured. | Medium | [.env](file:///Users/aldriknoel/EmoGrow/EmoGrow/.env) L28 | The database is accessible without authentication. | Use a strong password for database connections, even in development. |
| **OWASP A03: Injection — No server-side input handling** — Since no data is ever sent to the server, there are technically no injection vectors *yet*. However, the frontend constructs URL parameters unsanitized: `router.get('/edukasi/detail?id=${content.featuredId}')`. | Medium | [Edukasi.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Edukasi.tsx) L193 | When backend routes are added, unsanitized query params could lead to SQL injection or path traversal if not handled properly. | Use parameterized routes (`/edukasi/detail/{id}`) instead of query strings. Always sanitize/validate route params server-side. |
| **OWASP A04: Insecure Design — Health data stored in localStorage** — Child BMI scores, nutritional status, weight, height, and questionnaire answers are stored in `localStorage` which is accessible to any JavaScript running on the same origin. | High | [ScreeningAnak.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/ScreeningAnak.tsx) L48–55 | Any XSS vulnerability would expose children's health data. localStorage has no expiration, encryption, or access control. | Store health data server-side only. Never persist medical data in client storage. |
| **OWASP A05: Security Misconfiguration — APP_DEBUG=true** — Debug mode is enabled, which exposes detailed error pages with stack traces, environment variables, and database credentials. | High | [.env](file:///Users/aldriknoel/EmoGrow/EmoGrow/.env) L4 | If deployed with this setting, any error will expose internal implementation details, file paths, and potentially database credentials. | Set `APP_DEBUG=false` in any non-local environment. |
| **OWASP A07: XSS — No output sanitization concern** — React's JSX auto-escapes output by default, so there are no direct XSS vectors in the current code. However, the use of `dangerouslySetInnerHTML` should be monitored if added later. | Low | N/A | Currently safe due to React's default escaping. | Maintain vigilance. Never use `dangerouslySetInnerHTML` with user input. |
| **No CORS configuration** — Default Laravel CORS config is in use. No custom CORS configuration was found. | Low | N/A | Not a current risk since there are no API endpoints. Will need configuration when APIs are added. | Configure CORS restrictively when API endpoints are created. |
| **No rate limiting** — No rate limiting on login attempts or any route. | Medium | N/A | Brute-force attacks on login are possible (though login doesn't actually authenticate anyone currently). | Implement rate limiting on auth routes using Laravel's `throttle` middleware. |
| **No CSRF token validation visible** — While Laravel includes CSRF protection by default on POST routes, all current routes are GET-only closures. The auth form uses `router.get('/')` instead of `router.post()`, meaning CSRF protection is bypassed entirely. | High | [AuthPage.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Auth/AuthPage.tsx) L98–101 | Login/register actions use GET requests, which are not CSRF-protected. If this form ever sends real credentials, they'll appear in browser history and server access logs. | Use POST requests for all state-changing operations (login, register, form submissions). |
