# 03 — Frontend Audit

## Overview

The frontend is the only substantial part of this codebase. It consists of **12 page components**, **12 shared components**, and a global CSS design system. The UI is visually polished with a "neubrutalism" design language. However, all data is hardcoded, and there are significant structural and performance concerns.

**Tech:** React 19.2, TypeScript 6.0, Inertia.js React 3.1, Tailwind CSS 4.3, Recharts 3.8, Lucide React icons.

---

## Findings

| Finding | Severity | File/Line | Impact | Recommendation |
|---------|----------|-----------|--------|----------------|
| **Massive component files with no decomposition** — `AdminPanel.tsx` is **783 lines / 55KB**, `EdukasiDetail.tsx` is **54.7KB**, `Monitoring.tsx` is **464 lines / 32KB**. Multiple sub-components, data constants, and utility functions are crammed into single files. | Medium | [AdminPanel.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/AdminPanel.tsx), [EdukasiDetail.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/EdukasiDetail.tsx), [Monitoring.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Monitoring.tsx) | Hard to maintain, test, or reuse. Cognitive overload for developers. | Extract sub-components (e.g., `UserTable`, `DetailModal`, `FormModal`) into separate files. Move data constants to dedicated files or API calls. |
| **All data is hardcoded in components** — User lists, child data, chart data, activity lists, milestone tables, FAQ content, and education modules are all JavaScript constants inside page components. | Critical | [AdminPanel.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/AdminPanel.tsx) L45–67, [Monitoring.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Monitoring.tsx) L13–87, [Aktivitas.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Aktivitas.tsx) L21–78 | Data cannot be updated without code changes. Different users see identical data. The app provides no real functionality. | Replace all hardcoded data with Inertia page props passed from Laravel controllers backed by database queries. |
| **localStorage used as a pseudo-database** — Screening data (IMT score, status, age, weight, height, questionnaire answers) is stored in `localStorage` and read across pages (Dashboard, Edukasi, Aktivitas). User role is also stored in localStorage. | High | [ScreeningAnak.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/ScreeningAnak.tsx) L48–54, [Dashboard.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Dashboard.tsx) L107–108, [Edukasi.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Edukasi.tsx) L15–19 | Data is lost on browser clear, not available cross-device, and trivially manipulable by users. For a health app, this means medical data has zero integrity. | Persist all data server-side. Pass computed values via Inertia shared data or page props. |
| **No loading states on page navigation** — Inertia progress bar is configured (`color: '#4B5563'`) but individual page components don't show loading indicators when fetching data or transitioning. | Low | [app.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/app.tsx) L23–25 | Users may see blank or stale content during navigation. | Add Inertia `usePage` loading state detection and skeleton loaders per page. |
| **No error states or empty states for dynamic data** — Pages assume data always exists. There are no fallback UIs for when data is missing, API calls fail, or lists are empty (except the search-no-results case in Aktivitas and AdminPanel). | Medium | All page components | When real API integration happens, any failure will result in blank screens or crashes. | Add error boundaries, loading skeletons, and empty state illustrations for all data-dependent views. |
| **`typeof window !== 'undefined'` checks scattered everywhere** — SSR safety checks appear in Dashboard (L107–108), ScreeningAnak (L48, L63), Edukasi (L15–19), and Aktivitas (L120). These are boilerplate-heavy and fragile. | Low | Multiple files | Code noise, inconsistent application. Some localStorage reads don't have this check. | Create a utility function `getLocalStorageItem(key, defaultValue)` that handles the SSR check centrally. |
| **Sidebar resizing via mouse events without cleanup safety** — The Sidebar component attaches `mousemove` and `mouseup` listeners to `document` and properly cleans up, but `body.style.cursor` is set to `'col-resize'` during resize and may not reset if the component unmounts mid-drag. | Low | [Sidebar.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Components/Layout/Sidebar.tsx) L28–50 | Minor UX glitch: cursor might stay as resize cursor if sidebar unmounts during drag. | Reset cursor style in the cleanup function of `useEffect`. |
| **HelpDesk widget uses `window.location.pathname` as useEffect dependency** — This is a mutable object reference, not a reactive value. The effect will only run once on mount, not on Inertia navigation. | Medium | [HelpDeskWidget.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Components/HelpDeskWidget.tsx) L20–25 | The widget won't correctly hide/show when navigating to/from the login page via Inertia (no full page reload). | Use `usePage()` from Inertia to get the current URL reactively. |
| **No code splitting or lazy loading** — All pages are eagerly loaded via `import.meta.glob('./Pages/**/*.tsx')`. With 12 pages totaling 300KB+ of source, the initial bundle includes everything. | Medium | [app.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/app.tsx) L13 | Slower initial page load, especially on mobile. | Use dynamic imports: `import.meta.glob('./Pages/**/*.tsx', { eager: false })` for lazy-loaded page resolution. |
| **Recharts imported in full** — `Monitoring.tsx` and `LaporanEvaluasi.tsx` import multiple Recharts components. Recharts is a heavy library (~200KB gzipped). | Medium | [Monitoring.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Monitoring.tsx) L7–9, [LaporanEvaluasi.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/LaporanEvaluasi.tsx) L7–8 | Bundle bloat for pages that don't need charts. | Lazy-load chart-heavy pages. Consider tree-shaking or a lighter charting library for simple visualizations. |
| **Inconsistent design language** — Some pages use the "neubrutalism" style (thick borders, box shadows, uppercase text) while others (ScreeningAnakDetail, ScreeningAnakResult, Aktivitas) use a softer card-based design. Components like `Badge`, `Button` use Tailwind utility classes referencing CSS custom properties, but pages directly use hardcoded hex values. | Medium | Compare [Dashboard.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Dashboard.tsx) vs [Aktivitas.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Aktivitas.tsx) | Visual inconsistency across the app. Users experience two different design systems. | Establish a single design system. Either use neubrutalism everywhere or the softer style everywhere. Enforce through shared components, not inline Tailwind classes. |
| **External image dependencies** — `i.pravatar.cc` for user avatars and `images.unsplash.com` for activity images. These are third-party services that could be slow or unavailable. | Low | [Dashboard.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Dashboard.tsx) L111, [Aktivitas.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/Aktivitas.tsx) L26–72 | Images may fail to load, showing broken image icons. No fallback UI. | Host images locally or use a CDN. Add `onError` fallback handlers to `<img>` tags. |
| **TypeScript types are minimal** — Only `global.d.ts` (with `InertiaPage` type augmentation) and `vite-env.d.ts` exist. No shared types for domain entities (Child, Screening, Activity, User). Interfaces are defined inline in page components. | Medium | [types/](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/types), [AdminPanel.tsx](file:///Users/aldriknoel/EmoGrow/EmoGrow/resources/js/Pages/AdminPanel.tsx) L10–30 | Type duplication across files. Inconsistent shape definitions. Hard to maintain type safety. | Create `types/models.ts` with shared interfaces for all domain entities. |
